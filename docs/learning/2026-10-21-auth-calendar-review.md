# 로그인과 캘린더 안정성: 구현 검토 및 문답

작성일: 2026-10-21. 범위: 개선 항목 1~4. 현재 로컬 구현이며 운영에는 미반영.

## 문답 진행 방식

- `code-review`: 객관적인 오류와 제품 정책을 구분하고 실제 변경 코드와 근거를 확인한다.
- `debugging`: 예상 동작 → 가설 → 가장 작은 실험 → 결과 → 원인 순서로 진행한다.
- `examination`: 질문은 하나씩. 답을 먼저 받은 뒤 부족한 부분만 짚는다. 자신의 말과 구체적인 예로 설명한다.
- `retrieval`: 다음 주제로 넘어간 뒤 앞에서 다룬 개념을 새 사례에 적용한다.
- 사용자가 요청한 순서대로 구현을 먼저 끝내고 문답을 시작한다. 아래 질문의 정답은 미리 제공하지 않는다.
- 질문마다 관련 현재 소스의 최소 코드와 파일 링크를 먼저 보여준다. 구현, 가정한 상황, 변경 제안을 구분한다.
- 답변 전에는 이해했다고 판정하지 않는다. 문답이 끝나면 강점·약점·빠진 개념·확신도와 다음 연습 하나를 기록한다.

## 구현과 검증 근거

### 1. 로그인 토큰 노출

- JWT는 URL에 넣지 않고 POST 응답 본문으로만 전달한다.
- 60초 코드가 URL fragment에 들어가며, 프론트엔드는 교환 전에 주소를 지운다.
- HttpOnly 쿠키의 브라우저 바인딩과 코드가 함께 있어야 교환된다.
- DB에는 코드와 바인딩의 SHA-256 해시 및 사용자 ID·만료시각만 저장한다.
- 조건부 DELETE 결과가 1인 요청만 JWT를 받는다. 다른 브라우저의 실패는 유효한 코드를 소모하지 않는다.
- Nginx 로그에서 query/Referer를 빼고 콜백 요청은 기록하지 않는다.
- 기존 발급 JWT와 과거 접근 로그를 삭제·무효화한 것은 아니다.

읽을 코드:
- `src/main/kotlin/com/dong/daytous/service/LoginCodeService.kt`
- `src/main/kotlin/com/dong/daytous/repository/LoginCodeRepository.kt`
- `src/main/kotlin/com/dong/daytous/controller/LoginController.kt`
- `src/main/kotlin/com/dong/daytous/config/jwt/OAuth2AuthenticationSuccessHandler.kt`
- 프론트엔드 `src/features/auth/hooks/useLoginExchange.ts`, `src/features/auth/api/authApi.ts`, `nginx.conf`

검증: `LoginCodeServiceTest`, `LoginControllerTest`, `OAuth2LoginRedirectTest`, `SecurityIntegrationTest`, 프론트엔드 `useLoginExchange.test.tsx`. 임시 Nginx에 가짜 토큰을 넣은 요청으로 로그와 no-store/no-referrer 헤더도 확인했다.

### 2. 월을 걸치는 일정

- 시작일이 그달에 있는 조건을 기간이 겹치는 조건으로 바꿨다.
- 조회 구간은 월초부터 다음 달 월초 미만이다.
- 시간 일정의 종료는 제외 경계로 취급한다. 종일 일정은 DB에 마지막 포함 날짜를 저장한다.
- 시작과 종료가 같은 순간 일정도 해당 월에 표시한다.
- 다른 공간 및 삭제된 일정은 제외한다.

읽을 코드: `repository/ScheduleRepository.kt`의 `findOverlappingMonth`, `service/ScheduleService.kt`의 `getSchedules` (모두 `src/main/kotlin/com/dong/daytous/` 아래).
검증: `CalendarReliabilityTest`의 월 경계·월 전체 포함·자정·종일·순간·다른 공간 사례.

### 3. 삭제 후 재생성 방지

- 삭제할 때 행을 즉시 없애지 않고 `deletedAt`과 `PENDING`을 기록한다.
- 목록·단건·충돌 목록·알림 조회에서 삭제 기록을 제외한다.
- Google 삭제 실패 시 다음 배치에서 재시도한다. Google에서 같은 이벤트를 받아도 삭제 흔적을 확인하여 복원하지 않는다.
- 원격 삭제 완료 뒤에도 흔적은 유지한다. 실제 삭제된 이벤트라는 410 응답은 완료로 처리한다.
- 404는 리소스 없음뿐 아니라 접근 불가·잘못된 캘린더일 수도 있어 계속 대기한다. 403 등 다른 오류도 성공 처리하지 않는다.
- `@Version`으로 이미 삭제되기 전에 읽은 오래된 DB 객체가 나중에 저장되는 것을 차단한다.
- 이것은 DB 동시 갱신 보호다. 클라이언트 편집 폼의 버전 검증이나 외부 API의 모든 exactly-once 문제를 해결한 것은 아니다.

읽을 코드: `domain/schedule/Schedule.kt`, `service/ScheduleService.kt`, `service/ScheduleGoogleWriter.kt`, `service/GoogleCalendarSyncService.kt`.
검증: `CalendarReliabilityTest`의 삭제 실패→재수신→배치 재시도→재수신 흐름, 알림 제외 및 오래된 객체 저장 거부.

### 4. 재시도 설정과 원래 대상

- 즉시 전송과 배치 재시도가 `ScheduleGoogleWriter`를 공유한다.
- 매번 동기화 활성 여부와 방향을 확인한다. 비활성/GOOGLE_TO_APP이면 보내지 않고 대기를 유지한다.
- 아직 원격 ID가 없는 생성은 현재 선택한 캘린더를 사용한다.
- 원격 ID가 있는 수정·삭제는 기억한 계정과 캘린더를 사용한다. 이벤트 ID만으로 다른 캘린더를 수정하지 않는다.
- 구버전 행은 원래 캘린더가 비어 있다. 실제 가져오기나 성공한 전송으로 확인할 때 기록한다. 404만 보고 추측하여 확정하지 않는다.
- 인증정보가 없어 Google API 호출을 하지 못했으면 수정/삭제를 성공으로 표시하지 않는다.
- 변경되지 않은 원격 데이터를 가져와 재시도 대기 중인 로컬 수정을 덮어쓰지 않는다.

검증: `ScheduleGoogleWriterTest`의 캘린더 변경, 계정 선택, 비활성·방향, 410/403/404, 인증 없는 생성. `GoogleCalendarSyncServiceTest`의 배치 연결.
공식 오류 의미: https://developers.google.com/workspace/calendar/api/guides/errors

## 질문 순서 (답변을 받은 후 다음 질문)

1. [설명·보안] 기존처럼 JWT를 URL로 보내면 어떤 경로로 남을 수 있나? 지금 일회용 코드로 바꾼 이유를 실제 로그 사례 하나로 설명한다.
2. [실행 예측] 코드만 복사한 다른 브라우저와 원래 브라우저가 각각 교환하면 어떻게 되는가? 쿠키·해시·조건부 삭제 코드를 확인한다.
3. [동시성] 동일한 유효 요청 둘이 동시에 도착하면 `findById`가 둘 다 성공할 수 있다. 그래도 JWT가 하나만 나오는 근거는 무엇인가?
4. [경계] 60초가 지난 코드, 페이지 새로고침, React StrictMode 효과 재실행은 각각 어떻게 처리되는가? 실패 시 자동 재시도의 안전성을 비교한다.
5. [기간 예측] 10월 30일~11월 2일 일정이 11월 조회에 들어가는 조건을 자신의 말로 설명한다. 시작 또는 종료가 그달이라는 OR 조건만으로 충분한지 반례를 든다.
6. [경계 비교] 11월 1일 00시에 끝난 시간 일정과 11월 1일까지인 종일 일정이 왜 다르게 처리되는가?
7. [디버깅 가설] 앱 삭제 후 Google 연결만 실패했다. DB 행을 바로 지웠을 때 다음 가져오기에서 일어날 일을 예측한다.
8. [설계 비교] `deletedAt`과 `syncStatus`를 따로 갖는 이유를 설명한다. 화면에 없음과 원격 삭제 완료는 같은 상태인가?
9. [전이] Google 삭제는 됐지만 응답이 끊겼다. 다음 재시도에서 410/404/403이 오면 각각 어떤 증거가 부족하거나 충분한가?
10. [동시성] 동기화가 버전 3을 읽고, 삭제가 버전 4를 저장했다. 늦은 동기화 저장은 어떻게 처리되는가? 코드 교환의 조건부 DELETE와 공통점을 비교한다.
11. [정책] A 캘린더에 만든 일정이 실패 대기 중일 때 설정을 B로 바꾸면 새 생성과 기존 수정·삭제를 똑같이 다뤄도 되는가?
12. [설정] 재시도 전에 동기화를 끄거나 가져오기 전용으로 변경하면 무엇을 남기고 무엇을 하지 않아야 하는가?
13. [전이·회상] 삭제 흔적을 백업에서 복원하지 않으면 어떤 현상이 생길 수 있나? 예전에 학습한 DB 백업 개념과 연결한다.
14. [검증 설계] 이 변경을 배포하기 전에 실제 Google 계정에서 어떤 최소 시나리오를 확인할지 제안한다.

## 문답 후 필요하면 조정할 제품 정책

- 로그인 코드 유효기간 60초와 재로그인 안내.
- 삭제는 앱에서 즉시 숨긴다. 원격 삭제 대기를 보여주는 별도 UI는 이번 범위에 없다.
- 동기화가 꺼진 동안 작업을 대기시키고 켜면 재개한다.
- 원래 캘린더가 없는 구버전 데이터의 보수적인 처리와 재연결 안내 필요성.
- 삭제 흔적 보존 기간: 현재 자동 정리하지 않는다. 정리하려면 오래된 재수신과 복원 정책을 먼저 정해야 한다.

## 운영 적용 전

아직 푸시·PR·머지·운영 SQL 실행·배포하지 않았다. 1번 커밋 위에 2~4번 작업을 이어둔 로컬 브랜치다.

배포 시에는 1번 `scripts/add-login-code.sql`과 2~4번 `scripts/schedule-sync-reliability.sql`을 먼저 검토·적용해야 한다. `@Version` 도입 전후 서버가 동시에 쓰면 이전 서버가 버전 검사를 하지 않으므로 전환 중 쓰기/배치를 잠시 멈추는 배포 순서가 필요하다. 프론트엔드의 로그인 코드 교환 변경도 함께 반영한다.
실제 Google 계정의 연동, PostgreSQL 운영 마이그레이션, iPhone 로그인은 이번 로컬 검증에 포함하지 않았다.

## 최종 로컬 검증

- 백엔드 전체 214개 테스트 통과: 기존 200개 + 이번 회귀 사례 14개.
- `git diff --check` 통과. 프론트엔드 코드는 이번 2~4번 작업에서 변경하지 않았다.
- 외부 Google API는 모킹했다. 운영에 데이터나 설정을 적용하지 않았다.
